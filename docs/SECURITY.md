# GrantMatch trust boundaries

- **Evidence authority.** The funder designates the register and commits to its bytes before the claim. The register is a normalized statement from the grant administrator or an accepted payment-data custodian. Pinning proves that validators inspect the agreed bytes. The funder remains responsible for verifying who controls the source, whether the records are accurate and complete, and whether settlement later changes. The public demo uses fictional records.
- **Scope.** One instance records one claim in USD cents. It rejects duplicate canonical transfer IDs within a claim and inside the register. A grant program that shares transfers across multiple instances needs a common registry or allocation control. The evidence publisher is responsible for assigning one canonical ID per transfer and checking for aliases.
- **Evidence rules.** The register must use schema 1, with at most 100 rows, a maximum size of 32 KiB, and exactly the documented row fields. The claim allows at most 20 entries. Missing, mismatched, unsettled, out-of-window, and wrong-project rows receive explicit reason codes. Unavailable or invalid register data fails review without a decision so the same claim can be reviewed again if the committed bytes become available.
- **Consensus and finality.** Validators independently retrieve the commit-pinned JSON and compare the canonical decision using strict equivalence. The contract parses evidence as structured data and runs no language model. The dashboard reads finalized state and distinguishes a finalized receipt from successful execution.
- **Operational limits.** The contract records an eligibility decision. Payments happen in a separate funder workflow. StudioNet is a development network. Verify the funder, address, deployed source and applicable upgrade controls before using a result. Publish only data suitable for permanent public disclosure.
